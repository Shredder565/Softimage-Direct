# CMD-01-ADDONDOC: add-on documentation and wizard helper objects

Row: **CMD-01-ADDONDOC** (sub-row of CMD-01 / CMD-02 "Custom"). Status: **SPEC** for the
four plain commands and for the parts of the two helper objects that `PackageAddon` /
`PackageAddonUI` use; the page-building and code-generation methods of the helpers are
listed but not specified (see open questions).

## Shared facts

### Command flags (S, R)

All six: logging off (`siNoLogging`), return value on, no enable condition, never raise
on their own. `GetAddonDocHelper`, `WizardHelper`, `CreateXMLDoc`: key assignment off and
plug-in item category "Wizard". The other three are key-assignable. Only
`GetAddonDocPath` takes an argument.

### Add-on documentation files: answer to CMD-01b Q10 (S)

For an add-on whose folder is `<…>\Addons\<N>`, the four companion files live in that
folder's root and are named from the fixed prefix `netview_`:

| Role | File name | Format |
|------|-----------|--------|
| Documentation page | `netview_<N>.htm` | HTML |
| Icon | `netview_<N>.jpg` | JPEG (56×56 recommended by the wizard text) |
| **Description file** | `netview_<N>.txt` | plain text, the whole file is the description |
| **Detail file** | `netview_<N>.xml` | small XML file, below |

`<N>` is "everything after the first `\Addons\`" in the directory path given (on Linux
`/Addons/`). The match is case-sensitive, and a path without that segment gives an
empty name. For a nested path such as `…\Addons\A\B` the name is `A\B`.

**Detail file layout.** As written by the helper:

1. Line 1: the XML declaration, version `1.0`, no encoding attribute.
2. Line 2: a comment, `Generated by SimpleXMLDoc helper.  Executed <local date-time string> by <login name>` (two spaces before "Executed").
3. Root element `xsi_file` with three attributes in this order: `type="AddonInfo"`,
   `xsi_version="<Application.Version()>"`, `syntax_version="1.0"`.
4. One child element per dictionary entry, in dictionary order: the element name is the
   key, the element text is the value. Children are indented with one tab.
5. Root end tag. Every line ends with a line feed only.

Values and keys are written as they are: there is no XML escaping (a value holding `&`
or `<` produces a file that will not load again).

**Detail keys.** The default dictionary, in order: `Categories`, `PlatForms`, `Title`,
`AuthorName`, `AuthorEMail`, `Company`, `URL`, `Language`, `Summary`, `Usage`. All start
empty except `AuthorName`, which starts as the current login name (environment variable
`USERNAME` on Windows, `LOGNAME` otherwise). `PackageAddonUI` reads and writes
`AuthorName`, `AuthorEMail`, `Company`, `URL`; `PackageAddon` copies every key it finds
into the add-on's details.

**Reading the detail file.** The text is parsed as XML; every direct child of the root
becomes one dictionary entry (tag name → text; a repeated tag keeps the last value).
The root element's name and attributes are not checked. Any failure (missing file,
parse error, no root) is logged as a warning,
`loadAddonDetails failure - <file> - <reason>`, and the entries collected so far
(normally none) are returned. It never raises.

**Description file.** Written with the plain text writer below (overwrite, system code
page). Read back whole; an empty file reads as an empty string.

**`GenerateAddDocWizard(dir)`** (used by the plug-in tree "add documentation" action):

1. Builds a stand-alone custom property named "Add-on Documentation" with three string
   parameters: `AddonDescription` ("...Describe your Add-on Here..."), `AddonImage`
   (`<template folder>netview_Default.jpg`), `AddonHtmlTemplate`
   (`<template folder>netview_ADDONNAME.htm.template`).
2. Layout: tab "Info" with `AddonDescription` labelled "Description" (multi-line, height
   200), `AddonImage` labelled "Image" and `AddonHtmlTemplate` labelled "Template for
   html" (both file-path controls: open-file mode, file must exist, image-file flag set);
   tab "Help" with a static text naming the four files that will be created and a button
   "Show Add-Ons Page", which opens
   `<factory path>/Data/NetView_Database/L04_body/content/addons/default.htm` in Netview.
   Help page `cus_addons_AddonDocWizard`.
3. Opens it modally; title is message 7212 of dictionary `XSIPLUGINUI`. Cancel ends the
   method with nothing written.
4. On OK, in this order: write the description file; write the documentation page
   generated from the chosen template; copy the chosen image to `netview_<N>.jpg`
   (overwriting); write the detail file from the default dictionary; open the new
   documentation page with the `ShowFileForEdit` command.

### `GetAddonDocPath`

Argument `Path` (input, no default): full path of an add-on directory. Returns exactly
what the helper's `GetAddonDocPath(Path)` returns: the documentation page path, or an
empty string when the path is not under an `Addons` folder or holds no `netview_*.htm`.

### `GetAddonUpdateArray`

No arguments. Returns the helper's `CheckForAddonUpdates()` result:

1. Loads the XML document at
   `http://www.softimage.com/softwareupdate/ModTool7/autocontent.xml` synchronously.
2. Any failure (no network, parse error, no root element) logs a warning
   `Error checking for updates - <reason>` and the result is **null**. A document
   without a `lastmodification` child also gives null.
3. Otherwise, for every `content` / `item` entry, reading its children in file order: a
   `date` child sets the entry's date; a `template` child is checked against the
   installed `.xsitemplate` files (all three roots): the entry is out of date when no
   installed template path contains that name, or when the installed template's root
   attribute `Date` is earlier than the entry's date (logs `Updated addon found: <name>`,
   otherwise `<name> is up-to-date`); a `url` child is collected when the entry is out
   of date at that point.
4. Returns the collected URLs as a variant array (possibly empty).

Since that address no longer serves the file, the expected result today is the warning
and null *(inferred)*. AfterImage should not make the request: log the warning with a
"not reachable" reason and return null.

`CheckAndInstallAddonUpdates()` on the helper runs the same check, then for each URL
logs `Installing addon: <url>`, runs `UnInstallAddon` then `InstallAddon` on it (errors
ignored), and returns 0.

### `GetNbUpdatesPending`

No arguments. Runs the same check and returns the number of URLs. When the check
fails (null result) the command ends in a script error instead of returning 0
*(inferred from the missing null test)*.

Not specified in this row (Q3) |

**Template expansion.** The template is read as lines. `tokens` and `replacements` must
have the same length, else an error is logged and raised. Each token is a regular
expression replaced everywhere on each copied line, tokens applied in order. Output
lines are joined with line feeds. When `defines` (a list of names) is supplied, lines
that start with `@if NAME`, `@if !NAME`, `@elseif NAME`, `@else`, `@endif` are
directives and are never copied:

- `@if` opens a block that is copied when the name is in `defines` (inverted by `!`),
  and only if the enclosing block is being copied;
- `@elseif` / `@else` select the first branch of the block whose condition holds;
  later branches are skipped once one has been copied;
- blocks nest; `@endif` closes the innermost one;
- errors raised: `@elseif outside @if…`, `@else without @if…`, `@endifs without @if…`,
  `Missing @endif…`, each followed by `in template file '<path>'`.

Without `defines`, directive lines are treated as ordinary text.

### `CreateXMLDoc`

No arguments. Returns an empty XML document builder (`ObjType` `SimpleXMLDoc`).

| Member | Behaviour |
|--------|-----------|
| `CreateRootElement(name)` | creates, stores (as `documentElement`) and returns the root element; calling again replaces it |
| element `.SetAttribute(name, value)` | sets or replaces an attribute; attributes keep first-insertion order |
| element `.AddChild(name)` | appends and returns a child element |
| element `.text`, `.cdata` | leaf content; `text` wins, `cdata` is used only when `text` is empty |
| element `.name`, `.attrs`, `.children`, `.ObjType` (`SimpleXMLElement`) | readable state |
| `GetXMLAsString()` | the serialised document |
| `Save(file)` | serialises and writes with `TextToFile_NoThrow`; returns empty string or the failure message |

Serialisation: XML declaration line; the "Generated by SimpleXMLDoc helper." comment
line (date and login as in the detail file section); then the tree. An element with
children is written as a start-tag line, its children one tab deeper, and an end-tag
line. A leaf is one line: start tag, text (or a CDATA section), end tag; an empty leaf
is start tag immediately followed by end tag. Attributes are `name="value"` separated by
single spaces. No escaping anywhere. Every line ends with a line feed. Serialising
with no root element is a script error *(inferred)*.

### Enable conditions and errors

None of the six has an enable condition. Errors come only from the helper methods
as listed (file not found, write failures, template syntax).
